# SRS 开发日志：实测调优与 Bug 修复

> 日期：2026-03-21
>
> 项目：SRS (Spotify Recording Slicer)
>
> 前置文档：design/20260320.md

## 1. 背景

基于 20260320 设计方案完成首次实测。测试中发现两类问题：

1. **切分算法需要调优**：部分参数和硬约束在实际录音中表现不佳，需要根据实测结果调整
2. **WavSampleReader 存在 Bug**：录制文件的 WAV header 未正确更新时，duration 计算错误并导致 EOFException
3. **录制脚本问题**：进程管理不完善，终止时 playerctl 继续运行、输出杂乱

## 2. 切分算法调优

### 2.1 移除 maxDurationError 硬约束

**问题**：两首蔡琴的歌曲连续播放时，有声部分之间的静音非常大，谷底偏移显著。由于 `maxDurationError = 3.0` 硬约束的存在，这些歌曲的谷对被直接排除，导致切分失败。

**修改**：删除 `maxDurationError` 参数和 `findBestPair` 中的 `if (durationError > maxDurationError) continue` 过滤。

**取舍**：移除硬约束后可能导致错分，但由于难以界定一种需要明确拒绝的场景，主要依赖评分机制（w1=10 的高权重惩罚）来选择正确的谷对，否则可能会拒绝本可以切分的歌曲。考虑到每次切分完成后都会手工检查，比起避免错分，更希望程序能自动切分，并在失效时通过 `--margin` 参数手动介入。

### 2.2 评分权重调整

| 权重 | 调整前 | 调整后 | 理由 |
|------|--------|--------|------|
| w2（DBus 接近度） | 1.0 | 2.0 | 更偏好离 DBus 预期位置近的谷 |
| w3（谷深度） | 0.1 | 0.5 | 更偏好安静的（能量更低的）谷 |

理由同 2.1：在没有硬约束的情况下，需要评分机制更强地引导选择。提高 w2 和 w3 能够让评分更倾向于位置合理、能量更低的谷对。

### 2.3 postBottomTime 上限 1.0 → 2.0

**问题**：有时前一首歌曲结尾有较长的静音段，导致切分点向前漂移。

**修改**：`postBottomTime` 的上限从 1.0 秒改为 2.0 秒，能更好地缓解这个问题。

```kotlin
val postBottomTime = minOf((v2.endTime - v2.bottomTime) / 2, 2.0)  // was 1.0
```

### 2.4 新增 coerceAtMost 上界

**问题**：如果歌曲后面的静音太长，`rawCutPoint` 可能超出 v1 谷的范围，切到歌曲有声部分的开头。

**修改**：对 `rawCutPoint` 增加上界限制，确保不切头并留出余量：

```kotlin
val rawCutPoint = maxOf(
    v1.bottomTime, v2.bottomTime + postBottomTime - duration
).coerceAtMost(
    v1.endTime - minOf(
        0.3, (v1.endTime - v1.bottomTime) / 2  // 300ms 或半个谷宽度，取小值
    )
)
```

### 2.5 TransitionConfidence: MEDIUM → LOW

置信度只有两档，高/低比高/中更自然，改为 `HIGH` / `LOW`。

### 2.6 valleyThresholdFactor 0.05 → 0.01

**问题**：`valleyThresholdFactor = 0.05` 时，乐器或人声淡出的结尾也会被纳入谷的判定范围，导致谷的边界不准确。

**修改**：改为 0.01 后能更严格地界定谷的范围，缓解淡出误判的情况。

### 2.7 Pre-filter 逻辑放宽

**问题**：原先的判定条件 `abs(actualDuration - duration) <= 2.5` 要求录制时长和 Spotify 时长的差值在 ±2.5 秒以内。但由于 DBus 时间存在漂移，实际录制时长可能比 Spotify 时长更长，这些歌曲不应被过滤掉。

**修改**：

```kotlin
// before: abs(actualDuration - duration) <= 2.5
// after:
if (actualDuration >= duration || difference <= 3)
```

允许实际时长大于等于 Spotify 时长的情况，同时将差值容许从 2.5 秒放宽到 3 秒。

## 3. Bug 修复

### 3.1 WavSampleReader duration 错误与 EOFException

**现象**：ffprobe 显示录音时长为 `00:59:59.28`，但 WavSampleReader 报告 `12173` 秒，随后在读取样本时抛出 `EOFException`。

**根因**：录制命令使用 `-rf64 auto`，ffmpeg 在开始录制时将 data chunk size 写为占位值 `0xFFFFFFFF`，在录制结束时再回头更新。如果 ffmpeg 被终止时未能完成 header 更新，data chunk size 就会保持 `0xFFFFFFFF`（≈ 4.29 GB），导致 duration 计算虚高（`0xFFFFFFFF / 352800 ≈ 12173.9` 秒）。ffprobe 能正确处理这种情况（检测到 header 大小超过实际文件后使用文件大小计算），但 WavSampleReader 未做此检查。

**修复**：

1. **Clamp dataChunkSize**：`min(parsedDataSize, file.length() - dataChunkOffset)`，无论 header 是否正确都能得到正确的 duration
2. **用 blockAlign 替代 numChannels × bytesPerSample**：duration 计算、帧计数、seek 偏移全部改用 WAV 规范定义的 `blockAlign`，更准确地处理可能存在对齐填充的格式
3. **增加 blockAlign 校验**：`require(blockAlign >= numChannels * bytesPerSample)`
4. **新增 3 个测试**：验证 oversized header 被正确 clamp、读取不抛 EOFException、正确 header 不受影响

### 3.2 录制脚本改进

**问题**：

- `timeout` 终止录制时，`playerctl -p spotify metadata -F` 管道被信号杀死后，Bash 输出包含完整管道命令的 "已终止" 通知
- playerctl 进程未被显式终止，在 ffmpeg 停止后仍可能继续记录 timestamp
- cleanup 函数中的命令缺少 `|| true`，在 `set -e` 环境下可能导致 trap handler 提前退出
- 录制终止时未暂停 Spotify 播放

**修改**：

1. **FIFO 解耦**：playerctl 的输出通过命名管道（FIFO）传递给 while 循环，不再使用 shell 管道。这样 playerctl 作为独立的后台进程运行，PID 可被显式捕获和管理
2. **trap EXIT 替代 trap SIGINT SIGTERM**：无论脚本以何种方式退出（信号、正常结束、`set -e` 触发），cleanup 都会运行
3. **cleanup 顺序**：pause Spotify → kill playerctl → kill ffmpeg → wait → 清理 FIFO，每个命令加 `|| true`
4. **只处理 Playing 状态**：在循环入口统一过滤非 Playing 状态的事件
5. **跳过已有内容时的逻辑**：pause → sleep → next，避免继续播放已有的歌曲

### 3.3 文件名双引号处理

**问题**：Unraid NAS 在写入文件名包含英文双引号的文件时，自动将引号替换为下划线且不报错。这导致程序生成的文件名与 NAS 上实际的文件名不一致，无法跳过先前已处理的文件。

**修改**：`sanitizeAsFilename` 增加 `.replace("\"", "_")`，与 NAS 行为保持一致。
